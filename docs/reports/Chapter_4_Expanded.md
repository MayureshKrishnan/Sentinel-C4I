# PLANNED TASKS FOR NEXT PHASE & TESTING

Since a significant portion of the frontend architecture, backend routing, and security protocols have been successfully implemented in Stage-I, rigorous testing methodologies were applied to validate the current system state. Furthermore, a strict roadmap has been established for the subsequent development phases.

### 4.1 Planned Tasks for the Next Phase (Phase II)
The foundational C4I (Command, Control, Communications, Computers, and Intelligence) dashboard is currently operational. The next phase of development will focus strictly on algorithmic integration, persistent database migration, and offline hardware automation.

**1. Implementation of the AI Credibility Engine:**
The primary objective of Phase II is to translate the Spatiotemporal (Haversine) algorithm designed in Chapter 3 into executable Python code. This AI engine will act as a strict middleware filter in the FastAPI backend, automatically assigning a credibility score (0-100%) to all incoming public tips before they reach the officers.

**2. Database Migration (PostgreSQL & PostGIS):**
Currently, the dynamic case folders and active tips utilize local client-side state variables. In Phase II, the entire backend will be hardcoded to a localized PostgreSQL relational database. The PostGIS extension will be implemented to handle advanced spatial queries (e.g., calculating the radius of probability around a missing person's Last Known Position).

**3. Enterprise-Grade Security (Argon2id Hashing):**
While the current human-in-the-loop email webhook provides excellent perimeter security, Phase II will secure the internal database. All law enforcement passkeys will be cryptographically hashed using the Argon2id algorithm, ensuring resistance against GPU brute-force attacks and rainbow table breaches.

**4. LoRaWAN Autonomous Hardware Integration:**
To combat internet blackouts during disasters, physical ESP32 microcontrollers equipped with LoRa (Long Range) transmitters will be field-tested. These nodes will transmit offline distress coordinates to our newly developed `/api/v1/webhooks/lora` backend endpoint, completely bypassing the need for civilian cell towers.

### 4.2 Software Testing Methodologies
To ensure the reliability, security, and geographic accuracy of the Sentinel platform, multiple tiers of software testing were conducted during Stage-I.

**1. Unit Testing:** 
Individual software components (such as the Python `smtplib` email generator and the Leaflet.js map renderer) were tested in isolation. The objective was to ensure that the foundational scripts executed without raising internal exceptions or crashing the server thread.

**2. Integration Testing:** 
Integration testing verified that the separate architectural layers (Frontend HTML, Python FastAPI, and SMTP Email Servers) communicated securely. Specifically, we tested the JSON payload transfer from the `submit_tip.html` form to the backend endpoint to ensure data was not lost or malformed during transmission.

**3. Security & Access Control Testing:** 
Due to the sensitive nature of police intelligence, strict security testing was conducted on the Asymmetric Single-Page Application (SPA) router. The goal was to mathematically prove that unauthorized users could not bypass the `login.html` quarantine state without a cryptographic token generated by a verified email click.

**4. Usability & UI Testing:** 
The platform was tested across varying screen dimensions to ensure the Tailwind CSS grid correctly collapsed into a mobile-friendly view, ensuring that ground officers using tablets could still efficiently read the live tip feed and interactive heatmaps.

### 4.3 Executed Test Cases (Stage-I)

**Test Case 1: Civilian Geographic Intake Parsing**
* **Test Case ID:** TC-01
* **Objective:** Verify that the open-source Esri Map API correctly translates a civilian map click into mathematically valid Latitude and Longitude coordinates.
* **Pre-condition:** User accesses `submit_tip.html` with an active internet connection.
* **Test Steps:** User searches for "Mumbai, India" in the search bar and clicks on a specific street corner on the rendered map.
* **Expected Outcome:** The system should instantly drop a visual red pin and automatically populate the locked "Latitude" and "Longitude" text fields with 6-decimal floating-point numbers.
* **Actual Outcome:** Pin rendered successfully; coordinates populated with zero latency.
* **Status:** PASS

**Test Case 2: Zero-Trust Master Admin Webhook**
* **Test Case ID:** TC-02
* **Objective:** Validate that unregistered operatives are quarantined and that the Python backend successfully dispatches an SMTP authorization email to the Master Admin.
* **Pre-condition:** FastAPI backend is running; valid Gmail SMTP credentials are loaded in environment variables.
* **Test Steps:** An unregistered officer attempts to log into the Command Dashboard using a random Operative ID.
* **Expected Outcome:** The frontend UI displays a red `[QUARANTINE]` alert and blocks access. Simultaneously, the Python backend dispatches a high-priority HTML email containing `[APPROVE]` and `[REJECT]` buttons to the Commander's inbox.
* **Actual Outcome:** UI blocked access appropriately. The email was successfully received in the admin inbox within 1.5 seconds.
* **Status:** PASS

**Test Case 3: Admin Rejection Protocol**
* **Test Case ID:** TC-03
* **Objective:** Ensure that if a Commander clicks "REJECT" on the webhook email, the frontend strictly enforces a total clearance denial.
* **Pre-condition:** Officer is in a `[QUARANTINE]` state (from TC-02).
* **Test Steps:** Master Admin clicks the red `[REJECT & PURGE]` link inside the received email. Officer clicks 'Authenticate' again on the login screen.
* **Expected Outcome:** The backend registers a 'false' authorization token in local storage, and the UI displays a `[CLEARANCE DENIED]` fatal error, permanently locking the profile.
* **Actual Outcome:** The JavaScript route-guard correctly interpreted the rejection token and blocked access with the specified error.
* **Status:** PASS

**Test Case 4: Dynamic Case Folder Segregation**
* **Test Case ID:** TC-04
* **Objective:** Verify that selecting a different missing person folder dynamically updates the Subject Profile UI without requiring a hard page reload.
* **Pre-condition:** Officer is authenticated and viewing the `dashboard.html` interface.
* **Test Steps:** Officer clicks on the "[CASE-02] Sarah Jenkins" folder in the Active Case Directories sidebar.
* **Expected Outcome:** The Subject Profile component should instantly swap out the hardcoded name, age, and medical data of Arjun Mehta and replace it with Sarah Jenkins' data using DOM manipulation.
* **Actual Outcome:** The JavaScript event listener successfully intercepted the click and dynamically rendered the correct subject data.
* **Status:** PASS
